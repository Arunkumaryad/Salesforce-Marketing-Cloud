# 3. What is SQL Query Activity?

A **SQL Query Activity** retrieves, combines, filters, and transforms
information from Data Extensions and Marketing Cloud system Data Views,
then writes the result into a target Data Extension.

Salesforce describes it as a way to retrieve and unify data across Data
Extensions and system Data Views.

## Easy Explanation

Think of it as:

> **Read data → process data → save the required result.**

Example:

``` text
CustomerProfile_Arun
        +
TransactionData_Arun
        +
ProductSpecification_Arun
        ↓
       SQL
        ↓
SQL_DataExtension_Arun
```

SQL Query Activity is commonly used for:

-   Segmentation
-   Audience creation
-   Data transformation
-   Joining multiple Data Extensions
-   Combining Data Extensions with Data Views
-   Reporting
-   Email engagement analysis
-   Journey audiences
-   Automation monitoring
-   Preparing data for messaging

# 6. Data Extension

A **Data Extension (DE)** is a table-like structure used to store
customer or business data in Marketing Cloud.

It contains:

-   Fields / columns
-   Records / rows
-   Data types
-   Primary keys
-   Optional send relationships
-   Optional retention settings

Example:

  --------------- --------- --------- -------
  B36DEsubkey01   in        Bag       Zara
  B36DEsubkey02   usa       Laptop    HP

# 11. Primary Key

A primary key identifies a record uniquely.

Example:

``` text

```

If one row is expected per subscriber, `SubscriberKey` is a logical
candidate for the primary key.

Do not mark every column as a primary key. Salesforce recommends using
primary keys strategically because excessive primary keys can hurt
performance.

# 30. Important SQL Query Activity Rule

Avoid:

``` sql
SELECT *
```

especially with joins.

Salesforce's SQL Query Activity documentation says that a `JOIN` and
`SELECT *` cannot be used together in this activity; explicitly list the
columns instead.

Good:

``` sql
SELECT
    de1.SubscriberKey,
    de1.Country,
    de2.Product,
    de3.Brand
```

Also, Salesforce recommends selecting/dragging fields from the Data
Extension tree in the SQL editor so the activity can identify the
associated Data Extension correctly.

## 30A. SQL Activity Consideration (Screenshot Summary)

The training slide **"SQL Activity Consideration"** lists six rules to
remember:

> 1. "Write the query against any data extension or the data views
>    provided in the system."
> 2. "No more than 20 query activities are permitted in a single
>    automation step."
> 3. "You can retrieve up to six month of data from data views."
> 4. "When selecting data extension fields, ensure that the field names
>    match in the source and the target data extensions. The SQL query
>    activity doesn't raise an error for mismatched field names."
> 5. "Queries that include both a join and a SELECT * statement aren't
>    permitted. Instead, write a statement that specifies each column
>    name, even when there are multiple columns."
> 6. "Query Activity will timeout if ran more than 30 minutes."

### Easy explanation / memory table

  #   Rule                                   What it means in practice
  --- -------------------------------------- --------------------------------------------------------------
  1   Query source can be DE or Data View   A SQL Query Activity can read from a regular Data Extension **or** a system Data View (e.g. `_Open`, `_Sent`) — or both, joined together.
  2   Max 20 Query Activities per step      You cannot stack more than 20 SQL Query Activities inside a single automation step; split across steps if you need more.
  3   6-month Data View window              You can only pull up to six months of historical Data View data — older events are not retrievable via SQL Query Activity.
  4   Field names are NOT auto-validated    If a source field is `EmailAddress` but the target DE field is misspelled `EmaillAddress`, the activity will **not** error — it silently fails to populate that field. Always double-check names match exactly.
  5   No JOIN + SELECT *                    The moment your query has a JOIN, you must list every column explicitly; `SELECT *` combined with a JOIN is rejected.
  6   30-minute timeout                     Any SQL Query Activity that runs longer than 30 minutes will time out and fail — optimize long-running queries (fewer columns, narrower date range, better indexes/keys).

### Quick memory trick

``` text
Source   = DE or Data View
Limit    = 20 activities / step
Window   = 6 months of Data View history
Fields   = must match names manually (no auto-validation)
JOIN     = never with SELECT *
Timeout  = 30 minutes
```

# 35. Append

**Append** adds new query results to the existing target records.

Example:

``` text
Before:
A
B

Query:
C
D

After:
A
B
C
D
```

Typical use:

-   Event history
-   Logs
-   Incremental data
-   Historical records

------------------------------------------------------------------------

# 36. Update

**Update** updates matching target records and adds records when no
match exists.

Example:

``` text
Existing:
001 | Nike

Query:
001 | Adidas
002 | Puma
```

Result:

``` text
001 | Adidas
002 | Puma
```

The exact matching behavior depends on the target DE's key
configuration.

------------------------------------------------------------------------

# 37. Overwrite

**Overwrite** replaces the current target contents with the new query
result.

Example:

``` text
Before:
A
B
C

Query:
X
Y

After:
X
Y
```

The screenshot warns:

> **"Overwrite Data Action Selected. This action will overwrite all of
> the current data in the target data extension."**

Use Overwrite when the target should represent the latest/current
snapshot.

------------------------------------------------------------------------

# 38. Append vs Update vs Overwrite

  --------------------------------------------------------------------------
  Action            Existing Data      New Data          Typical Use
  ----------------- ------------------ ----------------- -------------------
  Append            Preserved          Added             Logs/history

  Update            Matching rows      New rows added    Incremental updates
                    updated                              

  Overwrite         Removed/replaced   New result        Current
                                       becomes target    audience/snapshot
  --------------------------------------------------------------------------

Salesforce notes that Append is often useful for event logs, Overwrite
is generally performant for many use cases, and Update can be less
performant.

# 42A. Full Step-by-Step Walkthrough — Querying a Data View into a New Target DE

This walkthrough follows a second, separate real example end-to-end:
querying the `_Open` Data View (email opens) into a brand-new target
Data Extension called `TestDataView_Arun`, running it, verifying the
result, then editing both the target DE and the query.

## Step 1 — Review existing Data Extensions in the folder

Open **Email → Subscribers → Data Extensions → Test Data - Arun**.

The folder lists the existing Data Extensions with their key
properties:

  Name                     Type       Sendable   Record Count   Last Modified Date
  ------------------------ ---------- ---------- --------------- -----------------------------------
  SQL_DataExtension_Arun   Standard   Yes        11              Saturday, October 03, 2026 11:11 AM
  CustomerProfile_Arun     Standard   Yes        11              Thursday, September 17, 2026 5:39 AM
  ProductSpecification_Arun Standard  No         11              Saturday, September 12, 2026 1:02 PM
  TransactionData_Arun     Standard   No         11              Saturday, September 12, 2026 12:07 PM

## Step 2 — Create a new target Data Extension

1. Click **Create** → **Create Data Extension**, and on the **"Specify
   the method by which the data extension will be built"** dialog,
   select **Standard Data Extension** (*"A standard data extension
   allows you to create custom fields to store data."*), then **OK**.
2. On the **Properties** step of **Create New Data Extension**, fill in:

``` text
Creation Method : Create from New
Name            : TestDataView_Arun
External Key    : (left blank — auto-generated)
Description     : (optional)
Type            : Standard
Location        : Test Data - Arun
Is Sendable?    : ✓
Is Testable?    : ✓
```

3. Click **Next** through **Data Retention Policy** and **Fields**, adding
   the fields: `SubscriberKey (Text, 50)`, `EventDate (Date)`, `Domain
   (Text, 50)`, `JobID (Text, 50)`, `IsUnique (Boolean)`, then save.

## Step 3 — Confirm the new DE was created correctly

Open `Data Extensions > Test Data - Arun > TestDataView_Arun`:

``` text
EXTERNAL KEY       : EE127756-352F-41BA-8C63-79AA72DD9B21
Status             : ✔ Available
Created Date        : Sunday, October 04, 2026 12:40 AM
Records             : 0
USED FOR SENDING    : Yes
USED FOR TESTING    : Yes
SUBSCRIBER RELATIONSHIP : SubscriberKey relates to Subscribers on Subscriber Key
```

Fields confirmed: `SubscriberKey`, `EventDate`, `Domain`, `JobID`,
`IsUnique` — 0 Records, since no query has populated it yet.

## Step 4 — Create the SQL Query Activity

1. In **Automation Studio**, open (or create) the automation
   `TestView__Arun`, drag a **SQL Query** activity into **Step 1**, and
   click **Choose**.
2. The **Choose SQL Query Activity** dialog lists existing queries
   (`Name`, `External Key`, `Target Data Extension`, `Update Type`,
   `Date Created`, `Date Modified`), e.g. `DemoSQL_Arun → SQL_DataExtension_Arun
   (Overwrite)`. Click **Create New Query Activity** instead of reusing
   one.
3. On **PROPERTIES**, name it (e.g. `TestDemoView__Arun`) and choose a
   folder location (e.g. `Query`).
4. On **QUERY**, write the SQL against the `_Open` Data View (visible
   in the Data Extension tree alongside your own DEs like
   `CustomerProfile_Arun`, `ProductSpecification_Arun`,
   `SQL_DataExtension_Arun`, `TestDataView_Arun`):

``` sql
SELECT SubscriberKey, EventDate, Domain, JobID, IsUnique
FROM _Open
WHERE JobID = 203612
```

   Click **Validate Syntax**, then **Next**.
5. On **TARGET DATA EXTENSION**, search and select `TestDataView_Arun`
   from the list (showing `Record Count: 0`, `Field Count: 5`), and
   choose the **Data Action**:

``` text
Append     — Add new data to your target data extension.
Update     — Update matching data, if found. If a record is not found, a new one is added.
Overwrite  — Replace or overwrite the current data in your target data extension.   ← selected
```

   Click **Next**.
6. On **SUMMARY**, review everything before saving:

``` text
Properties
  Name            : TestDemoView__Arun
  External Key    : (auto)
  Folder Location : Query
Target Data Extension
  Data Extension  : TestDataView_Arun
  Data Action     : ⚠ Overwrite
SQL Query
  SELECT SubscriberKey, EventDate, Domain, JobID, IsUnique FROM _Open
  WHERE JobID = 203612
```

   A warning banner reads: *"Overwrite Data Action Selected. This
   action will overwrite all of the current data in the target data
   extension."* Click **Finish**.

## Step 5 — Run the automation once and confirm

1. Back in the automation `TestView__Arun`, the activity now shows
   `1.1 SQL Query → TestDemoView__Arun` in **Step 1**. Click **Run
   Once**.
2. On the **Run Activities** screen, `Step 1 → 1.1 SQL Query →
   TestDemoView__Arun` is checked. Click **Run**.
3. A confirmation flow runs the query (same **Run Once Confirmation**
   pattern described in section 41) and executes immediately.

## Step 6 — Verify the result in the target Data Extension

Open `Data Extensions > Test Data - Arun > TestDataView_Arun >
Records`:

  SubscriberKey       EventDate                           Domain         JobID    IsUnique
  ------------------- ----------------------------------- -------------- -------- ----------

Three rows now exist — confirming the SQL Query Activity ran

## Step 7 — Add a new field to the target Data Extension

1. Open `TestDataView_Arun → Properties`, and click **Edit Fields**.
2. In the **Fields** editor, click the **+** button at the bottom-right
   to add a new row.
3. Name the new field `EmailAddress`, set **Data Type** to
   `EmailAddress`, **Length** `254`, then click **Save Fields**.
4. The **Fields** table now shows six fields: `SubscriberKey`,
   `EventDate`, `Domain`, `JobID`, `IsUnique`, and the newly added
   `EmailAddress`.

## Step 8 — Edit the existing Query Activity to add a JOIN

1. Back in the automation, click the dropdown arrow on the `1.1 SQL
   Query` tile. Three options appear: **Replace**, **Edit / View**,
   **Delete**.
2. Click **Edit / View** to open **Edit Query Activity**.
3. On the **QUERY** step, the Data Extension tree now shows top-level
   folders: `Data Extensions`, `Shared Items`, `Salesforce Data
   Extensions`. Update the SQL to join the `_Open` Data View with the
   `_Subscribers` Data View so you can also pull subscriber-level
   fields:

``` sql
SELECT o.SubscriberKey, o.EventDate, o.Domain, o.JobID, o.IsUnique
FROM _Open o
JOIN _Subscribers s ON o.SubscriberKey = s.SubscriberKey
WHERE o.JobID = 203612
```

4. Click **Validate Syntax**, then **Next** through **TARGET DATA
   EXTENSION** and **SUMMARY**, and **Finish** to save the updated
   query.
5. Run the automation again (**Run Once**) to refresh `TestDataView_Arun`
   with the joined result.

# 50. Important SQL Concepts

## SELECT

Choose columns.

``` sql
SELECT SubscriberKey
```

## FROM

Choose the source.

``` sql
FROM CustomerProfile
```

## WHERE

Filter rows.

``` sql
WHERE Country = 'IN'
```

## INNER JOIN

Return matching rows from both sources.

``` sql
INNER JOIN Orders
ON Customer.ID = Orders.CustomerID
```

## LEFT JOIN

Keep all rows from the left source and matching rows from the right.

## GROUP BY

Group records for aggregate calculations.

``` sql
GROUP BY Country
```

## HAVING

Filter grouped/aggregate results.

``` sql
HAVING COUNT(*) > 100
```

## DISTINCT

Remove duplicate result rows.

## CASE

Create conditional output.

``` sql
CASE
    WHEN Country = 'IN' THEN 'India'
    ELSE 'Other'
END
```

## COUNT / SUM / MIN / MAX

Aggregate functions.

# 51. INNER JOIN vs LEFT JOIN

### INNER JOIN

Only matching records:

``` text
A ∩ B
```

Example:

``` sql
FROM Customer c
INNER JOIN Order o
ON c.SubscriberKey = o.SubscriberKey
```

Only customers with matching orders are returned.

### LEFT JOIN

All records from the left table:

``` sql
FROM Customer c
LEFT JOIN Order o
ON c.SubscriberKey = o.SubscriberKey
```

Customers without orders are also retained.

### Interview Answer

> Use `LEFT JOIN` when you want all records from the primary/source
> table even if a related record does not exist in the second table.

------------------------------------------------------------------------

# 52. WHERE vs HAVING

### WHERE

Filters individual rows before grouping.

``` sql
WHERE Country = 'IN'
```

### HAVING

Filters grouped/aggregated results.

``` sql
GROUP BY Country
HAVING COUNT(*) > 100
```

This is a common interview question.

------------------------------------------------------------------------

# 53. NULL Handling

Correct:

``` sql
WHERE EmailAddress IS NULL
```

Correct:

``` sql
WHERE EmailAddress IS NOT NULL
```

Do not use:

``` sql
EmailAddress = NULL
```

# 54. Duplicate Records

Duplicates can be caused by:

-   Multiple transactions for one customer
-   Multiple opens
-   Multiple clicks
-   One-to-many joins
-   Duplicate keys in source DEs

Example:

``` text
Customer 001
   ↓
3 transactions
```

Joining customer to transaction may produce three rows for Customer 001.

Do not automatically use `DISTINCT` to hide duplicates. First understand
the relationship.

# 55. SQL Query Performance

Salesforce states that SQL Query Activities time out after **30
minutes**.

Optimization techniques include:

-   Select only required columns
-   Avoid unnecessary `SELECT *`
-   Reduce the data range
-   Use appropriate primary keys
-   Use compatible data types
-   Avoid unnecessary joins
-   Filter early where practical
-   Avoid concurrent access to the same datasets
-   Use staging/intermediate DEs for complex queries

Salesforce also recommends splitting large/complex queries into smaller
stages when appropriate.

------------------------------------------------------------------------

# 56. Data Staging

Instead of:

``` text
One huge SQL query
```

use:

``` text
Query 1
   ↓
Stage DE 1

Query 2
   ↓
Stage DE 2

Stage DE 1 + Stage DE 2
   ↓
Final Query
   ↓
Final DE
```

Benefits:

-   Easier troubleshooting
-   Smaller individual queries
-   Better performance
-   Easier maintenance

# 59. SQL Query Activity Interview Questions

### Beginner

**Q1. What is SQL Query Activity?**\
A: An Automation Studio activity used to retrieve, combine, filter,
transform, and store data from Data Extensions and Data Views.

**Q2. Where do you create it?**\
A:

``` text
Journey Builder
→ Automation Studio
→ Activities
→ Create Activity
→ SQL Query
```

**Q3. What is a target Data Extension?**\
A: The Data Extension where query output is stored.

**Q4. What is Append?**\
A: Adds new query output to existing target data.

**Q5. What is Update?**\
A: Updates matching target records and adds non-matching records.

**Q6. What is Overwrite?**\
A: Replaces the target contents with the new query result.

### Intermediate

**Q7. Can SQL Query Activity query multiple Data Extensions?**\
A: Yes, using SQL joins.

**Q8. Can it query Data Views?**\
A: Yes.

**Q9. Can Data Views and Data Extensions be joined?**\
A: Yes.

**Q10. Why can a JOIN create duplicates?**\
A: Because one source record can match multiple records in the joined
source.

**Q11. What is INNER JOIN vs LEFT JOIN?**\
A: INNER JOIN returns matching records only; LEFT JOIN keeps all records
from the left table.

\*\*Q12. Why avoid SELECT \*?\*\*\
A: It can retrieve unnecessary data and is not supported with JOINs in
the Automation Studio SQL Query Activity.

# 67. Best Practices

1.  Use meaningful SQL Query Activity names.
2.  Use meaningful target Data Extension names.
3.  Select only required columns.
4.  Avoid unnecessary `SELECT *`.
5.  Validate syntax.
6.  Test using **Run Once**.
7.  Verify target record count.
8.  Check duplicates after joins.
9.  Use primary keys strategically.
10. Keep matching fields compatible in data type.
11. Limit historical ranges when possible.
12. Use staging DEs for complex queries.
13. Avoid concurrent access to the same datasets.
14. Document important SQL.
15. Check Automation History after production runs.
16. Remember that valid SQL syntax does not guarantee correct business
    logic.
17. Do not treat Data Views as permanent historical storage.
